## 最初的两处疑问

1. 外层 `GetObj` 已经检查过空闲数量，为什么 `Pop()` 里面还要判断 `Count > 0`？
2. 如果进入 `Pop()` 时 `usedList` 已经达到 `maxNum`，再执行 `usedList.Add(obj)` 是否会报错？既然使用中已满，为什么不直接复用最早借出的对象？

## 先区分三个数量

| 表达式 | 含义 |
| --- | --- |
| `Count`，即 `stack.Count` | 当前空闲对象的数量 |
| `usedList.Count` | 当前借出、使用中的对象数量 |
| `maxNum` | 本次调用传入的数量上限，默认 50；不是 List 自身的容量限制 |

在同一个池内，正常获取和归还、没有重复记录时：

```text
池中对象总数 = 空闲数量 + 使用中数量
           = stack.Count + usedList.Count
```

`List<T>` 会按需要扩容，达到业务规定的 `maxNum` 并不会让 `Add` 自动抛出“已满”异常。`Add` 只是记录对象引用，不会创建 GameObject。容器能继续加入引用，与业务是否允许继续创建对象，是两件事。

## 外层条件实际在决定什么

```csharp
if (!poolDic.ContainsKey(poolName) ||
    poolDic[poolName].Count == 0 && poolDic[poolName].usedList.Count < maxNum)
```

按运算符优先级，含义是：

```text
没有这个池
或者
（没有空闲对象，并且使用中数量还没达到上限）
```

满足条件就实例化对象；否则调用 `Pop()`。

用户追问：“代码不是一直只拿使用中数量和 maxNum 比较吗？为什么说是在比较对象总数？”

解释：确实没有直接把两个数量相加。但在已有池的创建分支中，先要求 `stack.Count == 0`，这时对象总数就等于 `usedList.Count`。所以在决定是否继续创建的这一刻，只比较使用中数量就足够了。有空闲对象时，直接复用，不需要创建。

首次没有池是单独的分支；现有代码没有在这个分支检查 `maxNum` 是否为正数。因此本次正常上限推演以合法的正数为前提。

## 用户第一次自行推演的五种情况

这里“达到上限”指同一池的对象总数达到上限。推演假设每次使用相同的正数上限，且正常获取、归还，没有重复归还或外部修改容器。

| 情况 | 是否有池 | 空闲对象 | 总数是否达到上限 | 实际执行路径 |
| --- | --- | --- | --- | --- |
| 1 | 有 | 有 | 是 | 外层 `else` → `Pop()` 的 `if`，取空闲对象 |
| 2 | 有 | 无 | 是 | 外层 `else` → `Pop()` 的 `else`，复用最早借出的对象 |
| 3 | 有 | 有 | 否 | 外层 `else` → `Pop()` 的 `if`，取空闲对象 |
| 4 | 有 | 无 | 否 | 外层 `if`，创建新对象 |
| 5 | 无 | 无 | 尚无对象 | 外层 `if`，创建对象并登记新池 |

用户最初把情况 4 写成“外层 else”，交流中已纠正为“外层 if”。

用户由情况 2 正确解释了疑问 1：进入 `Pop()` 不保证栈里有空闲对象。如果取消内部判断，满额且没有空闲对象时也会执行空栈 `Pop()`，导致异常。

## 疑问 2：总数已满，不等于使用中列表已满

用 `maxNum = 3`，对象 A、B、C 举例：

| 操作后的状态 | 空闲栈 | 使用中列表 | 总数 |
| --- | --- | --- | --- |
| 已借出三个对象 | 空 | A、B、C | 3 |
| C 使用完毕并归还 | C | A、B | 3 |
| 再次获取 C | 空 | A、B、C | 3 |
| 继续获取，已无空闲 | 空 | B、C、A，A 被再次交给调用者 | 3 |

第三行先 `stack.Pop()`，再 `usedList.Add(obj)`，只是把 C 从空闲容器转移到使用中容器；对象总数没有增加。此时加入前的使用中数量是 2，并不是已经有 3 个。

如果同一个池已经有 3 个使用中对象，同时又有空闲对象，那么总数早已超过 3。在固定上限、正常取还且没有重复记录的推演中，不应出现这种状态。

第四行没有创建新对象：取出使用中列表首项 A，把其记录移到列表末尾，并返回同一个 A 引用。这是抢占使用中对象，不是等待 A 自然归还。

## 中途的误解与纠正

用户一度把外层创建条件为 false 理解成“对象总数一定小于上限”，随后又总结成“只有对象总数等于上限才进入 Pop”。这两种判断都不成立。

已有池时，不能继续走创建分支，可能是：

- 有空闲对象，无论总数有没有达到上限，都进入 `Pop()`。
- 没有空闲对象，并且使用中数量已经达到上限，进入 `Pop()` 复用最早借出的对象。

以 `maxNum = 3` 再对照：

| 空闲数 | 使用中数 | 总数 | 分支 |
| --- | --- | --- | --- |
| 1 | 1 | 2，未满 | `Pop()` 的 `if` |
| 1 | 2 | 3，已满 | `Pop()` 的 `if` |
| 0 | 3 | 3，已满 | `Pop()` 的 `else` |

“有空闲对象”也不意味着“使用中容器已满”。正常情况下，有空闲对象恰恰意味着使用中数量没有占满全部名额，所以可以把取出的空闲对象加入使用中列表。

## 用户最终确认的理解

用户通过再次自行描述确认了以下逻辑；表述中的“有没有空闲对象”已明确纠正为第一项的“没有空闲对象”：

1. 已有池，没有空闲对象，并且使用中数量小于上限：此刻总数还没达到上限，外层 `if` 创建并使用新对象。
2. 有空闲对象：进入 `Pop()`，优先取空闲对象。可能曾有对象执行完毕后归还，但整个池还没达到过上限；也可能池的总数已经达到上限。这两种情况都能直接复用空闲对象。
3. 总数已达到上限，而且没有空闲对象：全部对象都在使用中，复用使用中列表最前面的对象，并将其记录移到末尾。

一句话总结：外层决定“创建还是复用”；`Pop()` 内部决定“复用空闲对象，还是抢占最早借出的对象”。

## 理解成立的边界

- 上述总数推演要求同一个池使用固定的正数上限；最初 API 每次调用都可传不同的 `maxNum`。后续用户已优化为建池时从 `PoolObj` 读取并保存本池上限，见下文。
- 使用中列表的顺序表示最近一次借出或被抢占的先后；“最老”指列表首项，不是对象的创建时间。
- 抢占不会通知旧使用者，也不会自动取消旧协程、计时器或回调。旧使用者仍持有同一个对象引用。需要调用者接受这种策略，不能把它理解成适用于所有业务的安全复用。
- 当前鼠标示例每次借出都会安排约 2 秒后的归还。若同一类型在归还前超过上限而发生抢占，旧协程仍可能提前归还已被重新借出的对象，后续还可能重复归还。这是示例与抢占策略结合时的限制；低于上限的普通取还不触发它。
- 用户完成的是本轮分支理解；当前源码的运行检查结论单独记在学习进度中，不能用理解正确代替实现无缺陷。

## 后续优化：预制体配置上限

用户新增 `PoolObj : MonoBehaviour`，使用 `public int maxNum = 50;` 提供新组件默认值。实际预制体覆盖为 Cube 5、Sphere 3，并已保存组件和对应 `.meta`。

`GetObj` 不再要求调用者传上限。首次建池时，`PoolData` 从第一个对象的 `PoolObj` 读取配置，保存到自己的 `maxNum` 字段，之后根据本池配置判断能否继续创建。这样不会因不同调用者传不同上限而改变同一池的规则。

这里有两种读取时机：`maxNum = poolObjScript.maxNum` 在本次构造时执行一次，保存当时的配置；下述 `needCreate` 则在每次实际读取时重新计算。建池后修改实例组件上的 `maxNum`，不会自动同步到池的私有字段。

## 新疑问：为什么 needCreate 每次读取都有效

用户的问题：“新声明的 needCreate 不是只有在创建类的时候执行一次吗？为什么每次调用似乎都会执行？”

实际代码是：

```csharp
public bool needCreate => usedList.Count < maxNum;
```

它是表达式体只读属性，不是保存计算结果的布尔字段，等价于：

```csharp
public bool needCreate
{
    get
    {
        return usedList.Count < maxNum;
    }
}
```

读取 `poolDic[poolName].needCreate` 时，代码会执行 getter，以当前 `usedList.Count` 和已保存的 `maxNum` 比较。没有自动缓存第一次的计算结果。

以 Sphere 上限 3 为例：

| 实际读取属性时的使用中数量 | 返回结果 |
| --- | --- |
| 1 | `true` |
| 3 | `false` |
| 归还一个后变成 2 | `true` |

如果改成普通布尔字段，并在构造函数中执行 `needCreate = usedList.Count < maxNum;`，保存的就只是当时的结果；后续列表变化不会自动更新这个字段。用户最初“只在创建时执行一次”的理解适用于这种构造时赋值。

简记：属性的 `=>` 定义“如何计算”，每次读取再计算；构造中的赋值保存“计算结果”。是否每次 `GetObj` 都读取属性，还取决于外层条件的短路：没有池时先走 `||` 左侧，有空闲对象时 `&&` 左侧为 false，这两种情况都不需要读取 `needCreate`。

`needCreate` 本身只判断使用中数量；它与外层“空闲数量为 0”一起决定是否创建，不代表只看这个属性就能得知池的总数。
